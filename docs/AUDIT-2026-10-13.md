## 2. 🔴 今天修掉的 5.3 倍錯誤(最重要)

### 現象

使用者看到「已實現報酬 **−31.88%**」,以為策略崩了。

### 真實資料

`localStorage['usstock_portfolio_v1'].cashLog` 的 5 筆平倉:

| 代號 | 報酬 | 出場理由 | 持有天數 |
|---|---|---|---|
| LMT | −6.49% | 觸及停損 | 3 |
| RTX | −6.09% | 觸及停損 | 6 |
| AMGN | −7.88% | 觸及停損 | 24 |
| FCX | −9.54% | 移動停利 | 22 |
| CRM | −6.92% | 移動停利 | 17 |

### 錯在哪

`js/portfolio.js` 的 `perf()` 與 `stats()` 都是:

```js
nav *= (1 + (c.fraction ?? 1) * c.pnlPct);
```

`c.fraction` 是「**這個部位**賣掉幾成」(階梯減碼用),
**不是**「這個部位佔**帳戶**幾成」。全出場時 `fraction = 1`,
於是一筆 −6.5% 被當成「整個帳戶 −6.5%」複利。

```
顯示: 100 × 0.9351 × 0.9391 × 0.9212 × 0.9046 × 0.9308 = 68.12  → −31.88%
實際: 100 × (1−6.49/6%) × … (每筆佔 1/6)               = 94.00  → − 6.00%
                                                    放大 5.3 倍
```

同一時間的 6 檔未實現持倉其實是**賺的**:MPC +25.7%、PSX +16.7%、
TMO +13.0%、MRK −2.4%(META/AMD 當時快取不全)。

### 為什麼這個 bug 特別危險

它**不會報錯、不會壞掉**,只是給出一個看起來很合理的錯誤數字。
後果是使用者會根據一個假訊號關掉一個其實還在回測正常回撤範圍內的策略
(回測最大回撤 −23.7% 零成本 / −26.5% 含成本)。
**報錯的數字比沒有數字更危險。**

### 修法

```js
function navWeight(c) {
  return (c.fraction ?? 1) * c.pnlPct / DAILY_POS;   // DAILY_POS = 現行 preset 的 maxPositions
}
```

`perf()` 與 `stats()` 共用,兩個分頁永遠一致。
新增 `verify.mjs` 第 10 項行為測試釘住它,附反向測試(確認正確值與錯誤值分得開),
並在 selftest 加一個案例(把權重拿掉必須紅燈)。

### ⚠️ 修完之後仍然不是真實帳戶報酬

它假設「每筆都剛好押 1/6、而且當時滿倉」。**App 從來沒有記錄實際股數或資金**
(`portfolio.buy()` 的 `shares` 參數存在,但 `app.js` 從來沒傳過,所以永遠是 1)。
畫面上已經標明這是模型值。要算真的,得先做第 3 節的問題 C。

### 2026-10-14:外部審閱後的追加修正(兩輪)

**(1) 權重要記在「配置」當下 —— 修了兩次才對。**

第一輪:`navWeight()` 直接除以 `DAILY_POS`(現行 preset 的倉位數)。
把 `config.DAILY_PRESET` 從 `marcus`(3 倉)換成 `composite`(6 倉)之後,
**過去所有交易的歷史報酬會憑空被改寫成一半**,即使交易本身一個字都沒變。
→ 改成在 `sellPartial()` 平倉當下寫 `posWeight` 進 `cashLog`。

第二輪(審閱者指出第一輪仍然不對,正確):寫的時機是**平倉**,
所以「3 倉 preset 買進 → 持有期間換成 6 倉 → 平倉」會記成 1/6,
而正確答案是 1/3。**權重是配置時決定的,不是出場時決定的。**

現在:`buy()` 建立持倉時就寫下 `posWeight`,`sellPartial()` 直接複製。
買進前就存在的舊持倉、以及 2026-10-14 之前的舊 `cashLog` 都沒有這個欄位,
只能用現行值估 —— 那些紀錄會帶 `posWeightEstimated: true`,
`stats()` / `perf()` 回報 `estimatedWeights`,「今日」與「績效」兩個分頁
都照實寫出「其中 N 筆的權重是事後估的」。**估算值不冒充歷史實際值。**

**(1b) `sellPartial()` 的入口驗證(審閱者第二輪指出,成立)。**

`Math.min(fraction, size)` 擋得住超賣,擋不住負數與 NaN:
`Math.min(-0.5, 1) = -0.5` → `pos.size = 1.5`,部位反而**變大**;
`Math.min(NaN, 1) = NaN` → 部位與 `cashLog` 一起被汙染,之後每個統計都是 NaN。

現行呼叫端傳的都是 preset 裡的正數,從那裡進不來。真正的入口是
localStorage 被汙染 —— `pos.size ?? 1` 的 `??` 只擋 null/undefined。
已在 `sellPartial()` 開頭驗證 `fraction` / `pos.size` / `price` / `pos.entryPrice`
都必須是有限數且 > 0,不合法一律拒絕,且**不寫 `cashLog`、不動持倉、不存檔**。
(price / entryPrice 不在審閱者列的清單裡,但是同一類的洞:NaN 價格會讓
`pnlPct` 變 NaN,整條資金曲線跟著變 NaN,而且不會有任何錯誤訊息。)

**(2) 「未滿倉會不會偏樂觀」—— 不會,已用引擎的模型確認。**

`backtest-real.js:181` 是 `const alloc = Math.min(nav / maxPos, cash);` ——
每個名額固定配置 NAV 的 1/N,**空缺的名額就留現金,不會重新分配給現有持倉**。
所以持 3 檔時每檔仍是 1/6、另外一半是現金,除以 6 正確。
(會偏樂觀的是「把資金平均分給現有 3 檔」那種模型,這套策略不那樣做。)

### ⚠️ 仍然存在的建模誤差:逐筆複利 ≠ 投資組合報酬

現在是把每一筆平倉事件依序乘進 NAV。但多檔同時持有時,它們**不是**
依序發生、每段都能把整個帳戶再投入的獨立期間。正確做法是每日把所有持倉
與現金標記市值、算一條每日 NAV 曲線(`backtest-real.js` 的 `equity` 就是那樣),
但實盤端**沒有每日資料** —— App 只有在你打開它的那幾天才看得到價格。

以目前的量級,兩種算法差 **0.15 個百分點**(逐筆複利 −6.00% vs 逐筆相加 −6.15%),
不影響結論;但部位變大、報酬變大時誤差會放大。
**要根治,前提是問題 C(持倉記錄股數與成本)+ 一條每日 NAV 紀錄。**

> ⚠️ **這個 0.15 個百分點只適用於「已實現總報酬」這一個數字,不能外推。**
> 審閱者第二輪明確指出這點,成立。總報酬是路徑無關的終點值,所以兩種算法
> 差得少;**最大回撤、Calmar、夏普全都是路徑相依的**,它們的誤差跟
> 總報酬的誤差沒有任何關係,目前**完全沒有量過**。

### 🔴 「績效」分頁的「最大回撤」本來不是回撤 —— 已改名

這是審閱者第二輪抓到的第三點,而且比他說的更嚴重。`perf()`:

```js
log.forEach((c, idx) => {
  nav *= (1 + navWeight(c));
  equity.push({ i: idx + 1, nav, ... });     // ← 橫軸是「第幾筆交易」
});
equity.forEach((e) => { peak = Math.max(peak, e.nav); maxDD = Math.min(maxDD, e.nav / peak - 1); });
```

兩個缺陷疊在一起:

1. **未平倉部位不在曲線上**(審閱者指出的)。
2. **橫軸是交易序號,不是日期**(更根本)。一月平倉的那筆和十二月平倉的
   那筆被畫成相鄰兩點,中間的時間、以及當時未平倉部位的浮動,
   在這條曲線上都不存在。

從這種序列算出來的數字,在任何意義上都不是回撤 —— 它是「已平倉事件依序
複利後最深的一段凹陷」。而畫面上它被標成 **`最大回撤`**,沒有任何限定詞。

已改名為 **「平倉序列最深凹陷」**,並在畫面上寫明橫軸是交易序號、
不計未平倉、以及「回測分頁的最大回撤是每日 NAV 算的,那個才是回撤,
兩者不能互相引用」。

**真正的修法是每日 NAV 重建,刻意暫緩** —— 審閱者給的四步法技術上可行,
但在問題 C 完成之前,它會產出一條看起來像真實績效、實際上仍是回測假設的
曲線。先把標籤改對,比先蓋一條更精緻的錯誤曲線正確。

### ✅ B. Monte Carlo 不可重現(2026-10-14 已修)

舊版:

```js
for (let b = 0; b < nBlocks; b++) starts.push(Math.floor(Math.random() * (n - blockSize)));
```

這一行有**兩個**錯,第二個是審閱者第二輪抓到的:

**(1) 沒有種子。** 同一份資料、同一份程式,每次跑出來的「幾比幾」都不同。
專案文件裡抱怨的抖動(5/6 → 4/6 → 3/6 → 6/6分不出 → 1/6)有一部分是真的
抽樣雜訊,但**無法區分「資料變了」與「骰子不同」**。
不變量 6 是人工閘門 —— 一個不可重現的閘門,證據力是打折的。

**(2) 少一個合法起點。** 合法起點是 `0 … n-blockSize`(共 `n-blockSize+1` 個),
這個寫法只給到 `n-blockSize-1`。**最後一個合法起點永遠抽不到** —— 也就是
「包含最後一筆日報酬的那個完整區塊」不可能出現在任何一次重抽樣裡。

> 量級誠實講:n≈3900、blockSize=20,3878 個起點少 1 個,對中位數的影響
> 約等於零。這個錯的危險在**另一個方向** —— 回測視窗一縮短,被排除的尾段
> 佔比就會放大,而且跟現在一樣不會有任何徵兆。

**已改:**

- `xorshift32()` 可重現 PRNG(種子 0 是不動點,有非零 fallback)
- `MC_SEEDS` = 5 顆**事先指定、寫死在原始碼裡**的非零種子。
  寫死是刻意的:跑之前才挑種子等於沒有固定種子。
- `blockStarts()` 範圍改為 `(n - blockSize + 1)`
- 每顆種子各自推進序列,但 A/B 在同一輪拿到**同一組起點** ——
  paired block bootstrap 的配對設計完整保留
- 表格數字是 5 顆種子的樣本**併起來**算的(5000 次)
- 新增「跨種子穩定度」區塊,回報每個姿態的 A−B 中位數與 A 較優比例的
  跨種子範圍,以及**符號有沒有翻轉**

**為什麼要多顆種子:** 固定種子只是**必要**,不是充分(審閱者指出,成立)。
單一固定種子只是把雜訊凍結成某個特定值,不會讓它消失 —— 你會得到一個
很穩定、而且可能剛好運氣好的答案。跨種子極差就是「只跑一顆種子」會承受的
抖動量,它不會因為把種子寫死而消失,只會變成**看不見**。

**驗證(`verify.mjs` 第 12 項):** 抽樣範圍用**定值 rng 證明邊界對應**

#### 不換資料源還能做什麼 —— 審閱者的回答(接受)

我問的是「這個結果有多少機率是真的?有沒有辦法在不換資料源的前提下檢驗?」

**嚴格答案:不能。** Bootstrap 只能分析既有資料在特定抽樣假設下的不確定性,

| 檢驗 | 做法 | **它解決不了什麼** |
|---|---|---|
| **時間外測試** | 事先保留一段從未用於決策的期間,在該期間比較 A/B/C/D 的相對表現 | 測得到**時間穩健性**,完全測不到生存者偏差 —— 保留期間的股票池還是今天的贏家 |

## 4. 今天另外兩個被量錯的數字

### 「12 分 22 秒」實際是 10.3 秒(錯 72 倍)

UI 上寫六姿態 A/B 要跑 12 分鐘以上。實測:
**純運算(前景分頁、同步、不含計時器)10.3 秒**,加上讀 IndexedDB 約 12~15 秒。

原因是 Chrome 的背景分頁計時器節流:`runAllPresetsMCInner` 中間有 **25 個 `await sleep()`**
(每個 preset 4 個 + 開頭 1 個),背景分頁的 `setTimeout` 被壓到每秒一次、
閒置 5 分鐘後每分鐘一次 —— **25 × 30 秒 ≈ 12 分鐘**。

同一份程式同一份資料實測兩邊:前景 20 秒跑完 12 組;背景(`document.hidden === true`)
同樣的事超過 4 分鐘才跑到 11 組。

**寫「要等 12 分鐘」會讓使用者以為當掉而關掉分頁 —— 等於這個功能不存在。**
已改成「約 10 秒,但別切到背景」。

### 手續費對 Calmar 的影響被低估

事前用解析法估算 0.25% 手續費的影響,CAGR 估 14.0%(實測 14.14%)、
15.7 年倍數估 7.8×(實測 7.99×),**都在誤差內**;
但 Calmar 估 0.59、**實測 0.534**,低了 10%。

原因:估算時假設了「最大回撤不變」,而實際上 maxDD 從 −23.69% 惡化到 **−26.45%** ——
